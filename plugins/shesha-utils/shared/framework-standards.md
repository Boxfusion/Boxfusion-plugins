# Framework standards: fix it the Shesha / ABP way

BoxFusion systems are built on **Shesha** (on ABP, NHibernate, FluentMigrator). The framework has a native, supported way to do most things. Claude, and developers new to the framework, tend to reach for custom JavaScript, raw SQL scripts or direct database edits instead. These shortcuts work today, then drift between environments, bypass the framework's tooling, and get overwritten or lost on the next deployment.

**The rule:** every fix uses the framework's native mechanism. A shortcut is allowed only in a genuine emergency, recorded as such in the PR, with a follow-up task to do it properly. When the native route has limits, treat them as caveats to handle, not as reasons to bypass it.

The same standard applies when **inspecting**: a place where the system bypasses the framework is a finding in its own right, with "what good looks like" pointing to the native mechanism.

## What to use

| Need | Native mechanism | Not this |
|---|---|---|
| Ship form changes | **`.shaconfig` config package** (`packageYYYYMMDD_HHMM.shaconfig`, embedded in the module's `ConfigMigrations`, imported once at startup by Shesha's seeder), built from the **environment's current form version** | Editing forms by hand in each environment; SQL updates to form markup; packaging an old repo copy (it downgrades newer live forms) |
| Reference lists, settings, notification types and templates | `.shaconfig` packages (`reference-list`, `setting-configuration`, notification config items); `shesha-settings` and `shesha-notifications` patterns | Hand-made rows in each environment; SQL inserts |
| Endpoint permissions | `[AbpAuthorize]` with permission names in code; `api-permissions-manifest` items in a package for configured rows; `permission-definition` items for page permissions | Raw SQL migrations writing `Frwk_PermissionedObjects` |
| Generic CRUD permissions per entity | `entity-config` items in a package (their import sets Get/Create/Update/Delete permissions), or the module's `api-permissions-manifest` where entity-config can't be used (see caveats) | SQL; leaving the default "any authenticated" |
| Row-level rules ("whose records may I see") | **Specifications** (`shesha-specifications`, global specifications) and one shared scope service | Filtering in each endpoint; trusting client parameters |
| Validation | **Fluent validators** on the server (`shesha-fluent-validators`) | Rules only in form scripts |
| Business actions | App service methods: one command per business action, in one unit of work (`shesha-app-layer`) | Multi-call writes from form scripts through generic CRUD |
| Side effects (SMS, email, events) | Shesha notifications; ABP unit-of-work completed handlers or domain events after commit | Sending inside the save transaction |
| Reference numbers | `shesha-ref-numbers` | Custom sequence tables, or numbers drawn in validators |
| Schema changes | FluentMigrator migrations following Shesha conventions (`domain-model`): real UTC timestamps, `OneWayMigration` where appropriate | Hand-run SQL scripts |
| Form behaviour | Shesha components, actions and data sources configured in the designer; small scripts only where no component or action exists, written to `clean-form-config` rules | Large custom JavaScript replacing what a component does |
| Background work | Shesha scheduled jobs (`ScheduledJobBase`) and Hangfire through the framework | Ad-hoc timers, or scripts run by hand |
| Message bus and integrations | The framework's hosted bus (`AddMassTransit` with its hosted service), per-environment Shesha settings, named `IHttpClientFactory` clients | A module building and starting its own bus or HTTP clients at start-up |
| Data repairs | Idempotent `OneWayMigration`s | Hand-run repair scripts |
| Guarding the permission model | An **authorisation inventory test** in CI that fails on Inherited or "any authenticated" endpoints not on an agreed allow-list (`checks/security.md` SEC-C) | Relying on reviewers to notice a missing `[AbpAuthorize]` |

## Known caveats (from real fixes; verify for the version in hand)

- **Read the developers' own code comments for framework workarounds.** When the system carries a hand-rolled workaround for a framework limitation, the previous developer has often already diagnosed it in a comment (e.g. "Shesha's `SignalRProvider` builds its `HubConnection` without an `accessTokenFactory`, so the hub handshake is anonymous and targeted notifications never arrive — so we open our own authenticated connection"). Treat such comments as leads: confirm the limitation against the pinned DLL, then route it to the Shesha team report. Grep for `workaround`, `hack`, `Shesha`, `TODO`, `framework` in both back-end and front-end source.
- **Packages overwrite, and can't be rolled back on their own.** A package import upserts and overwrites admin-saved rows, and sets imported permission rows `Hardcoded = false`. Hand-author packages to contain only the intended items. Exporting a whole module from a configured database would overwrite production's entire module configuration.
  - **Rollback:** before each import, take a read-only export of the rows the package will touch (in each target environment). Every PR's rollout notes name that export and how to re-import it.
  - **At most one open package per form across all PRs.** Two PRs built from the same live version undo each other on import. Give each form one owner until its package is merged.
- **Compare forms by content, not version number.** A package's `VersionNo` is the authoring environment's number; the importing database assigns its own, and an import can create version N+1 with identical markup. Normalise the markup JSON before comparing, and record which package holds the live content.
- **Versioned configuration items must be looked up with a live filter.** Forms, notification types and other configuration items have several versions; a lookup by `Name` without a `VersionStatus` (Live) or `IsLast` filter picks an arbitrary version once there is more than one.
- **Framework table and schema names move between versions — never hardcode them; derive them.** Through 0.44.x the framework tables are Pascal/underscore in `dbo` (`Frwk_ConfigurationItems`, `Core_ShaRoles`, `Frwk_UserLoginAttempts`, `Frwk_EntityProperties`, `Frwk_ReferenceLists`). **On 0.45.x they moved to a `frwk` schema with snake_case names** (`frwk.configuration_items`, `frwk.roles`, `frwk.role_permissions`, `frwk.setting_configurations`, `frwk.form_configurations`, `frwk.entity_properties`, `frwk.reference_lists`, and the login-attempts canary is `frwk.user_login_attempts`). A grep or SQL query keyed on the old names returns **nothing** on 0.45 and the area wrongly reads as "fine". **Rule:** resolve the real table/schema name for the version in hand from the decompiled entity's `[Table(..., Schema=…)]` / `[JoinedProperty(..., Schema=…)]` attributes (ilspycmd) before writing any query or grep, and state the version. The check files give the pre-0.45 names as examples only.
- **Shesha 0.43–0.45 app-service methods (custom) aren't virtual.** ABP's interceptors (authorisation, unit of work, validation) don't run when a test calls a hand-written service method directly (confirmed non-virtual through 0.45.1; CRUD-base overrides are virtual as always). Prove access control over HTTP; wrap direct calls in a unit of work. In-process dynamic DTOs may come back with an empty Id.
- **Shesha 0.43.x–0.44.x settings endpoints** (confirmed through 0.44.2; re-verify per version). `Settings/GetValue` and related reads can be anonymous and return secret settings; `UpdateUserValue` can overwrite global values. Probe every system (`checks/security.md` SEC-I).
- **Shesha notifications are sent after commit** for types not marked time-sensitive (`IsTimeSensitive`). Check this before claiming a "sent before the save committed" bug.
- **Integration package defaults.** Some packages fall back to a shared host (and even a shared username) when no setting is saved, e.g. the MassTransit integration's default broker. Inventory defaults as well as saved values (`checks/operations.md` OPS-H), and add a start-up guard that refuses known defaults outside Development.
- **Testing packages by version.** `Shesha.Testing` exists only from 0.46. For 0.43 systems use the standalone test infrastructure from `create-integration-tests` (see the caveats in `references/skills-to-use.md`).
- **Shesha 0.43.38–0.44.x bug (likely fixed on 0.45 — re-verify).** Re-importing an `entity-config` for an entity with a list property (an ItemsType child of the same name, e.g. `PermissionedEntities`) inserts a duplicate on `uq_Frwk_EntityProperties_Path`. The seeder rethrows and **the application fails to start**. For those entities, ship CRUD permission rows in the module's `api-permissions-manifest` instead. This is a Shesha team report item. **On 0.45.1 the mechanism is refuted by decompile:** the table is `frwk.entity_properties` with no surfaced `Path` column (so no `uq_..._Path`), and `EntityConfigImport.MapPropertiesAsync` is now an upsert on `(Name, EntityConfig)` iterating only top-level properties — the blind insert is gone. Treat the caveat as `<= 0.44.x`; on 0.45+ confirm with a re-import before relying on either behaviour.
- **Build forms from the live version.** Form packages must be built from the **environment's current version**, not the repo copy. Environments often run newer versions than the repo holds.
- **Compare with production before shipping.** Check a package against production (read-only, an approved copy or export) for unintended differences.
- **Version-pinned skills.** Use the plugin matching the system's Shesha version (e.g. `shesha-developer-0-43`). If a needed skill is missing for that version, follow the closest version's rules and note the gap.

## In briefs and PRs

- Every engineer brief says: **"Use the framework's native mechanism. No custom scripts or direct database edits where Shesha/ABP provides a way."**
- Every PR description states which native mechanisms it used, e.g. "permissions via `package20261027_1130.shaconfig`, no migrations". Any emergency shortcut is stated, with its follow-up task, and is listed in the report's emergency shortcuts register (native end state, follow-up trigger).
- Every PR that ships a package includes the pre-import export for rollback in its rollout notes.
